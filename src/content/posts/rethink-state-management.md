상태 관리는 프론트엔드의 영원한 화두다. Redux, MobX, Zustand, Jotai... 새 라이브러리가 나올 때마다 "우리 프로젝트에 뭘 써야 하지?"라는 질문이 반복된다.

그런데 최근 들어 나는 그 질문 자체가 잘못됐다는 생각이 들었다. 올바른 첫 질문은 **"이 상태는 누구의 것인가"**다.

## 상태는 두 종류로 나뉜다

### 1. 서버 상태 (Server State)

서버에 원본이 있는 데이터다. 사용자 목록, 게시글, 좋아요 수 같은 것들이다. 특징은 이렇다.

- 원본이 서버에 있고 클라이언트는 **캐시**를 들고 있을 뿐이다.
- 여러 사용자가 같은 데이터를 본다.
- 언제든 최신 값으로 바뀔 수 있다.

이런 상태에는 캐싱, 재검증(revalidation), 낙관적 업데이트 같은 기능이 필요하다. React Query(TanStack Query) 같은 도구가 정확히 이 문제를 푼다.

```ts
const { data, isLoading } = useQuery({
  queryKey: ['posts', postId],
  queryFn: () => fetchPost(postId),
  staleTime: 30_000, // 30초간 캐시를 신선하다고 여긴다
});
```

### 2. 클라이언트 상태 (Client State)

클라이언트가 원본인 데이터다. 모달이 열렸는지, 사이드바가 접혔는지, 입력 폼에 뭘 적었는지 같은 것들이다.

- 원본이 클라이언트 자신이다.
- 다른 사용자와 공유되지 않는다.
- 서버가 알 필요가 없다.

이런 상태에는 Zustand 같은 가벼운 스토어면 충분하다. 심지어 대부분은 컴포넌트의 `useState`로 끝난다.

```ts
const useSidebarStore = create((set) => ({
  isOpen: false,
  toggle: () => set((s) => ({ isOpen: !s.isOpen })),
}));
```

## 상태 관리 라이브러리의 역할

흔히 저지르는 실수는 **서버 상태를 전역 스토어에 넣는 것**이다. API 응답을 Redux로 들고 있으면 이런 일이 벌어진다.

1. 언제 다시 fetch해야 하는지 직접 관리해야 한다.
2. 로딩/에러 상태를 액션마다 손으로 작성해야 한다.
3. 캐시 무효화 로직이 액션 사이에 흩어진다.

서버 상태와 클라이언트 상태는 문제의 성격이 다르고, 따라서 도구도 나뉘는 게 자연스럽다.

> 라이브러리 선택은 마지막 문제다. 먼저 상태를 분류하고 나면 필요한 도구는 자연스럽게 보인다.

## 정리

- 서버 상태 → 캐시로 다룬다 (TanStack Query, SWR)
- 클라이언트 상태 → 가볍게 들고 있다 (useState → Zustand 순으로 최소한부터)
- 두 상태가 섞이는 순간(예: 낙관적 업데이트)이 진짜 어려운 문제다. 그때가 프레임워크의 도움을 받을 때다.

라이브러리 논쟁에서 내려와서 상태의 소유권부터 따져보자. 코드가 머리로 읽히는 순간, 상태 관리는 더 이상 무섭지 않다.
